# vexelray-installer

Turns a native-image executable and/or a compiled uberjar into a one-line installer served
from a public GitHub repo.

Part of the [VexelRay](https://sibarum.github.io/) stack. Building an application on it? Start at the [developer guide](https://sibarum.github.io/vexelray-framework/developers/).

```
your build ──► installer:generate ──► install.ps1  uninstall.ps1  update.ps1  diagnose.ps1  manager.ps1     (windows)
                                  ├─► install.sh  uninstall.sh  update.sh  manifest.linux.txt            (linux)
                                  ├─► manifest.json  README.md
                                  └─► staged artifacts ──► installer:publish ──► GitHub release
```

Windows and Linux are supported, each from a section of its own in the config, with its own binaries: a
project gives a `windows` section, a `linux` section, or both. The generator is platform-neutral and
`manifest.json` is organised per platform; macOS arrives as another `PlatformTarget` with its own templates.

## Modules

| Module | What |
| --- | --- |
| `installer-core` | Build-tool-independent library: config and manifest model, `PlatformTarget`s, templates, GitHub release publisher. Also a runnable CLI jar (`-cli` classifier) for non-Maven projects. |
| `installer-maven-plugin` | Goals `installer:generate` and `installer:publish`. |

Build and test everything: `mvn install` (Java 21+). End to end on Windows:
`powershell -File tests\smoke.ps1`. The installer windows: `powershell -File tests\window.ps1` and
`powershell -File tests\suite-window.ps1` (they drive them with the mouse, so they need an unlocked desktop).
End to end on Linux: `sh tests/linux-smoke.sh`.

## Use from Maven

```xml
<plugin>
  <groupId>dev.vexelray.installer</groupId>
  <artifactId>installer-maven-plugin</artifactId>
  <version>0.1.0-SNAPSHOT</version>
  <executions><execution><goals><goal>generate</goal></goals></execution></executions>
  <configuration>
    <publisher>Example Inc</publisher>
    <windows>
      <binaries>
        <binary>
          <attached>main</attached>          <!-- the project's own (shaded) jar -->
          <file>myapp.jar</file>
          <javaMin>21</javaMin>
          <shortcuts><label>MyApp</label><startMenu>true</startMenu></shortcuts>
        </binary>
        <binary>
          <name>myapp-native</name>
          <source>target/myapp.exe</source>   <!-- e.g. from native-maven-plugin -->
          <addToPath>true</addToPath>
        </binary>
      </binaries>
    </windows>
  </configuration>
</plugin>
```

A complete example is in [tests/maven-sample](tests/maven-sample/pom.xml).

1. `mvn package` runs `generate`: the files to commit land in `target/installer/`, the
   artifacts to upload in `target/installer-assets/<version>/`.
2. `mvn package installer:publish` also creates the GitHub release `v<version>` and uploads the
   artifacts (token in `$GITHUB_TOKEN`, or the variable named by `-Dinstaller.tokenEnv`). Add
   `-Dinstaller.dryRun` to see what would be uploaded. `publish` is never bound to a phase.
3. Commit `install.ps1`, `uninstall.ps1`, `update.ps1`, `diagnose.ps1`, `manager.ps1`, `manifest.json` and `README.md` from
   `target/installer/` to the project repo (or point `outputDirectory` at a checkout of it); with a `<linux>`
   section, `install.sh`, `uninstall.sh`, `update.sh` and `manifest.linux.txt` too.
   The README contains the one-liners:
   ```powershell
   irm https://raw.githubusercontent.com/owner/project/main/install.ps1 | iex
   ```
   ```sh
   curl -fsSL https://raw.githubusercontent.com/owner/project/main/install.sh | sh
   ```

A `<linux>` section takes the same fields as `<windows>`, with Linux builds as its binaries: a native image built
on Linux, the same uberjar, a `.tar.gz` where Windows has a `.zip`. Built on a Linux machine, they come from its
`target-linux/`; built elsewhere, point `source` at them.

Every run merges into the existing `manifest.json`, so every version ever published stays in its
`versions` history; `latest` is the highest non-prerelease. If `README.md` in the output dir was
not generated by this tool, the generated one is written as `INSTALL.md` instead.

### Plugin parameters

Defaults come from the project: `id` = artifactId, `name` = project name, `description`,
`version`, and `repo` from a github.com `<scm>` url.

| Parameter | Meaning |
| --- | --- |
| `id`, `name`, `publisher`, `description`, `version` | metadata; `id` is lowercase letters, digits, `. _ -` |
| `replaces[]` | `{id, repoPath}`: the ids this application was installed under before a rename, and where their generated files were committed in the same `repo`. See Renames below |
| `repo`, `branch`, `repoPath` | where the generated files are committed (`repoPath` for a subfolder); branch defaults to `main` |
| `releasesRepo`, `tagFormat` | where binaries are downloaded from; defaults `repo` and `v{version}` |
| `issuesUrl` | where people report problems; the diagnostic report says to attach itself there. Default: `https://github.com/<repo>/issues/new` |
| `windows.installDir` | default `%LOCALAPPDATA%\Programs\{name}` |
| `windows.registryDir` | where install manifests live; default `%LOCALAPPDATA%\vexelray-installer\installs` |
| `windows.binaries[]` | `source` *or* `attached` (`main` or a classifier), `name`, `file`, `kind` (`native`/`jar`/`archive`/`file`, inferred from the extension; a `.zip` is an archive, and a `.txt`, `.md`, `.html`, `.pdf` or `.rtf` a file), `dir`, `version`, `addToPath`, `icon` (an `.ico`, or a square `.png` of 256px or more that is converted to one; used by the shortcuts and the Apps entry), `shortcuts {desktop, startMenu, label, gui}`, `javaMin` (jars), `jvmArgs[]` (jars; placed before `-jar`), `runtime` (jars; id of an install that provides `binjava.exe`, found through the registry at launch), `exposes` (archives; `{command: path-inside-zip}`, recorded under `commands`), `signedBy` + `signerThumbprint` (native exes; see Signing), `fileAssociations[] {extension, description, contentType, icon}` (not archives; see File associations) |
| `windows.requires[]` | `{id, min}`: installs that must be present first. A binary's `runtime` is required implicitly. The installer refuses, before changing anything, if one is missing or older than `min`; the uninstaller warns when removing something another install still needs |
| `windows.system` | what the computer must have: `windows` (oldest version, `10.0.19041` or a build number), `memoryMb`, `diskMb` (free on the install drive), `vulkan` (`1.3`), `vulkanExtensions[]`, `d3d12` (feature level, `11_0` to `12_2`). The GPU fields must all be met by one GPU: its Vulkan device, and the DXGI adapter with the same LUID. See Diagnostics |
| `linux.installDir` | default `$HOME/.local/opt/{id}`; starts with `/`, `~/`, `$HOME/` or `$XDG_DATA_HOME/`, and may use `{id}` and `{name}` |
| `linux.registryDir` | where install manifests live; default `$XDG_DATA_HOME/vexelray-installer/installs` (`~/.local/share/...`) |
| `linux.binaries[]` | as `windows.binaries[]`, except: an archive is a `.tar.gz` (or `.tgz`), whose `exposes` paths are checked against it; an `icon` is a square `.png` (an `.ico` gives its largest PNG frame), shipped as `<name>.png`; `shortcuts.startMenu` is a menu entry, `shortcuts.desktop` a launcher in the Desktop folder if there is one, and `shortcuts.gui` (default true) is `Terminal=false`; `addToPath` links the command into `~/.local/bin`; `signedBy` does not apply; `appId` is the name the program's windows go by (`WM_CLASS`, or the Wayland `app_id`), which names its desktop entry `<appId>.desktop` and is its `StartupWMClass`, so a dock shows the running program under its icon (see Renames below) |
| `linux.requires[]` | as `windows.requires[]` |
| `linux.system` | `glibc` (oldest, `2.31`), `memoryMb`, `diskMb`, `vulkan`, `vulkanExtensions[]` (one Vulkan device must have them all, read from `vulkaninfo`) |
| `linux.arch` | what `uname -m` must say; default `x86_64` when there is a native binary or an archive, none for jars and files |
| `outputDirectory`, `assetsDirectory` | default `target/installer` and `target/installer-assets` |
| `notes`, `baseUrl`, `assetBaseUrl`, `skip` | release notes; URL overrides for testing; skip the goal |

## Use without Maven

```
mvn -pl installer-core package
java -jar installer-core/target/installer-core-0.1.0-SNAPSHOT-cli.jar --config installer.json \
     --version 1.2.0 --out dist [--publish]
```

`installer.json` has the same fields as the plugin configuration; see
[installer.example.json](installer.example.json). Relative `source` paths resolve against the
config file. `--platform linux` (or `windows`, or both, comma-separated) generates only those sections, so the other
platforms' binaries need not exist: for trying one platform's installer where only its build is at hand. It cannot be
combined with `--publish`, since a release has every platform.

## Suites: one command for several applications

Applications that ship together can share one install command and one page of instructions, while each stays
an install of its own (its own folder, record, Apps entry, updater and uninstaller), published from its own
repo exactly as above. A suite names its members by their `installer.json`:

```json
{
  "id": "vexelray", "name": "VexelRay", "description": "...",
  "repo": "owner/site-repo", "repoPath": "docs/install",
  "members": [
    { "config": "../vexplore/installer.json", "page": "../apps/vexplore.html" },
    { "config": "../text-editor/installer.json" }
  ]
}
```

```
java -jar installer-core/target/installer-core-0.1.0-SNAPSHOT-cli.jar --suite suite.json --out docs/install
```

writes `install.ps1` and `README.md` (the install page), and needs neither the artifacts nor the network.
Commit both to `repo`/`repoPath`. The suite's `install.ps1` installs nothing itself: for each member, in the
listed order, it fetches the member's published `manifest.json`, downloads the member's own `install.ps1`,
refuses it unless it matches the SHA-256 the manifest records (`tools.install.ps1`), and runs it. A member
whose manifest is not published yet is skipped and reported. `INSTALL_ONLY=a,b` limits the run to some
members. `INSTALL_NO_SHORTCUTS`, `INSTALL_NO_PATH`, `INSTALL_NO_ASSOCIATIONS`, `INSTALL_FORCE` and `INSTALL_SKIP_CHECKS` pass through to
every member; `INSTALL_VERSION` and `INSTALL_DIR` name one application, so they are set aside.

When any member has a `linux` section, the suite also gets an `install.sh` (`curl -fsSL <url> | sh`) and the page
a Linux part: the same plan, run through each member's own `install.sh` against its `manifest.linux.txt`, with the
same `INSTALL_*` variables (set for the `sh`: `curl -fsSL <url> | INSTALL_ONLY=a,b sh`) and
`sh -s -- --install-everything`. It has no window. A member with only a `windows` section is left out of it and
said to have no Linux version, and one with only a `linux` section out of `install.ps1`.

Run from a console a person is at, the suite installer opens one window, under the same rules as an
application's (`INSTALL_QUIET=1` or `-Quiet`, `CI`, `-NonInteractive` or redirected output keep it in the
console). It first reads every member's manifest, then shows a box for each member with the version it would
install (and the installed one), ticking those in `INSTALL_ONLY`, or else those not installed or out of
date; a member that is not published yet is shown but cannot be ticked. Below them, shortcut, PATH and
file-type boxes (only those some member has) apply to every member: they start from `INSTALL_NO_*`, or else
from the members' last installs, and when those disagree the box starts indeterminate, which leaves each
member its own choice. Install then shows a row per member (waiting, installing, installed, failed, not
selected, not published yet), a status line and bar, and the log the console gets; the end page names what
was installed and what was not, with **Open report** when a member wrote a diagnostic report. The members'
installers still run quietly inside it, in the same process: their output is copied into the log, and their
downloads show their progress in the suite's window, where Cancel stops them (a member already placing its
files finishes, and the rest are not started). Unmet system requirements are refused rather than asked about,
as in any quiet install; `INSTALL_SKIP_CHECKS=1` installs anyway. `page`
(optional) links a member's name on the install page; `manifestUrl` (optional) overrides the URL derived from
the member's `repo`, `branch` and `repoPath`. `version` (optional) pins the member: the suite installs that
version instead of the manifest's `latest`, and reinstalls it even when it is the one installed, since a snapshot is
rebuilt under the same version. A suite whose members are all pinned to snapshots is a preflight: every snapshot
built together, installable with one command while the public command keeps installing the releases. The install
page then lists each member's version. `optional: true` leaves a member out unless asked for, for a demo or an
application not ready yet: its box starts unticked, and a run without the window skips it, unless it is installed
already (then it is kept up to date like the rest) or `INSTALL_ONLY` names it. The install page names the optional
members, and the landing page tags their cards. A pinned member is never optional, so a preflight installs everything.
`--install-everything` (or `INSTALL_EVERYTHING=1`) treats the optional members like the rest, and `--do-not-prompt-me`
is `-Quiet`. Arguments need the script run from a file or as a script block, since `irm | iex` passes none:
`& ([scriptblock]::Create((irm <url>))) --install-everything --do-not-prompt-me`. Both pages show that line.

### A landing page

A suite can also have a page of its own, served by GitHub Pages from a repo of its own (`owner.github.io`, say),
so the command is short and the first thing people find:

```json
{
  "site": {
    "url": "https://owner.github.io",
    "badge": "0.1.0 · prerelease",
    "tagline": "One line under the name.",
    "requirements": "Needs Windows 10 or 11.",
    "feedbackUrl": "https://github.com/owner/repo/issues/new",
    "accentColor": "#2563eb",
    "logo": "site/mark.svg",
    "heroLogo": "site/mark-full.svg",
    "heroAction": { "label": "What it is built on", "url": "https://owner.github.io/tech.html" },
    "links": [ { "label": "Docs", "url": "https://owner.github.io/docs/" } ],
    "footerLinks": [ { "label": "Licenses", "url": "https://owner.github.io/licenses.html" } ],
    "notice": "Small print at the foot of the page, such as trademark notices.",
    "linux": {
      "url": "https://github.com/owner/repo/releases", "label": "Download for Linux",
      "text": "what there is to download.", "requirements": "Needs X11 and a Vulkan driver.",
      "steps": [ "Download the build.", "Run `chmod +x app`, then `./app`." ]
    },
    "sections": [
      {
        "id": "build", "title": "Build your own", "nav": "Developers",
        "lede": "A paragraph under the title.",
        "cards": [ { "stat": "1 line", "title": "Start", "text": "What it is.", "url": "https://owner.github.io/docs/start.html" } ],
        "action": { "label": "Read the guide", "url": "https://owner.github.io/docs/" }
      }
    ]
  },
  "members": [
    { "config": "../vexplore/installer.json", "page": "...", "image": "shots/vexplore.png", "imageAlt": "What it shows" }
  ]
}
```

```
java -jar installer-core/target/installer-core-0.1.1-SNAPSHOT-cli.jar --suite suite.json --site --out ../owner.github.io
```

writes `index.html`, a copy of the suite's `install.ps1` (so the command is `irm https://owner.github.io/install.ps1 | iex`),
each member's icon and screenshot under `img/` (and `site.logo` as `img/logo.svg` or `.png`, `site.heroLogo` as `img/hero-logo.svg` or `.png`), and `.nojekyll`. Only
`site.url` is required. The page is dark, with the name over a live backdrop that draws only while it is on screen;
`site.heroLogo` is set large beside the name, to its right on a wide screen and above it on a narrow one. It shows the
command with a copy button (and `site.heroAction` as a button under it), a card for each member (its screenshot, or its icon when it has no `image`; its
`description`), and what the install changes on the computer, worked out from the members' configs: install
folders, shortcuts, the commands added to `PATH` and the applications that register file types. Each of
`site.sections` goes between the members and those details, as a title, a paragraph, a row of cards (a card's `url`
is optional, and so is its `stat`, a figure set large above its title) and an optional button. The header links only the members and `site.links`, never a section. Text in the config
may use `` `code` ``; everything else is escaped. `site.footerLinks` go in the footer after the source link, and
`site.notice` is set in small print under them. When members have `linux` sections, a switch above the command,
starting on the visitor's own system, chooses between the Windows line and the Linux one (`curl -fsSL <site.url>/install.sh | sh`,
with `install.sh` written beside the page), and an *On Linux* detail says what it changes and how to choose and
uninstall; `site.linux.requirements`, if set, goes under the Linux line. Without Linux members, `site.linux`
offers Linux builds for download instead: the switch chooses between the install line and a button to
`site.linux.url` with its `text` and `requirements`, and its `steps` become one more of the details (without
script there is no switch, and both are shown). A `site.linux.url` beside Linux members is refused. The page
needs at least one member with a `windows` section. The members' manifests stay where their own runs published them,
so installs and updaters are the same whichever command installed them. Publish the folder from its repo's root with
GitHub Pages (**Settings > Pages > Deploy from a branch**).

## What the generated files do

- **install.ps1** reads `manifest.json`, downloads each binary, verifies its SHA-256, then
  places files, unblocks them, writes a `<name>.cmd` launcher for each jar, creates shortcuts,
  registers file types, optionally edits the user PATH, and registers an Apps & features entry.
  Nothing is written to the install dir until every download has verified. Options:
  `INSTALL_VERSION`, `INSTALL_DIR`, `INSTALL_NO_SHORTCUTS`, `INSTALL_NO_PATH`,
  `INSTALL_NO_ASSOCIATIONS`, `INSTALL_FORCE`, `INSTALL_SKIP_CHECKS`, `INSTALL_QUIET`, `INSTALL_CLOSE_APPS`. The `NO_*` choices in effect are stored in the
  install record (`options`), and updates and reinstalls keep them; `INSTALL_NO_*=0` opts back in.
  Run from a console a person is at, it opens a WinForms window: the folder and the shortcut, PATH and
  file-type choices (filled from the options above and the last install), then a progress bar and the same
  log the console gets, then **Start** (the first shortcut), or for a failure the error, **Open report** and a
  link to `issuesUrl`. Unmet system requirements are asked about rather than refused, and Cancel stops any
  time before files are placed. `INSTALL_QUIET=1` (`-Quiet`), `CI`, `-NonInteractive` or redirected output
  keep it in the console; `update.ps1` and suite installs always run their installers quietly (a suite has a
  window of its own; see Suites).
  Placing files is a transaction. Every file it writes (binaries, launchers, tools, shortcuts, the record)
  first moves the one it replaces into `.vi-backup-*` in the install folder (or `<registryDir>\..\backup\`
  for files elsewhere), after a line in `<registryDir>\<id>.journal` says so. The same goes for files the new
  version drops and for the PATH entries and file types it adds. The record is written last, then a commit
  line. A failure before the commit plays the journal backwards ("1.2.0 was put back as it was"); a run that
  was killed is rolled back, or finished if it committed, by the next one. Moving aside is a rename, so a
  running `.exe` is replaced in place (its old copy is removed by the next run). A file held open, such as a
  jar a JVM has, is offered to be closed: the window asks, `INSTALL_CLOSE_APPS=1` closes the processes
  started from the install folder, and otherwise the install fails and is rolled back. `<id>.lock` allows
  one install of an application at a time. With `INSTALL_EVENTS=1` it also prints `##vi {json}` lines (step,
  phase, progress) for a program following it.
  Downloads run up to four at a time into `<registryDir>\..\cache\<sha256>.part`, which becomes
  `<sha256>` once the hash matches. A dropped or stalled connection is retried three times from where it
  stopped (a `Range` request), and an install that was stopped carries on from there the next time; a file
  already in the cache is not downloaded again. What an install did not use is removed after its commit,
  and anything older than two weeks before the next one.
- **manager.ps1** (`manager.cmd`) is one window for every install in `registryDir`: installed and available
  versions, and **Update**, **Change...** (folder, shortcuts, PATH, file types), **Remove** and **Update all**
  (dependencies first). Each install copies its `manager.ps1` to `<registryDir>\..\manager\` when it is newer
  (by its `vi-manager-rev` line) and adds a Start menu shortcut, `<publisher> apps` (unless shortcuts are
  opted out); the last uninstall removes both. The manager changes nothing itself: it runs the
  application's own `install.ps1` (from its manifest, checked against the SHA-256 there) or `uninstall.ps1` in
  a quiet child process, one at a time, and follows its events. It asks before closing what is running from
  an install folder. Cancel stops a job only while it downloads. `-List`, `-Update <id>`, `-UpdateAll` and
  `-Remove <id>` (with `-CloseApps`) do the same in the console.
  The window is Microsoft Edge in app mode (no browser chrome, its own profile in `manager\edge`) showing a
  page the manager serves on `127.0.0.1` at a random port, behind a 64-character random token in the path.
  Requests must carry exactly that `Host` (against DNS rebinding), and changes must be POSTs from the page's
  own origin with an `X-Vi` header, which another site cannot send without a preflight the server never
  answers. The manager ends when the window closes or stops polling, after a change that is placing files
  has finished. Without Edge, or with `-Forms`, it opens the same window in WinForms.
- **diagnose.ps1** (`diagnose.cmd`) checks the computer against `windows.system` and writes a text report
  for bug reports to `<registryDir>\..\diagnostics\<id>-<time>.txt` (the last ten are kept; `-Out`, `-Copy`,
  `-Json`): Windows edition and build, processor, memory, disk, GPU scheduling, power; each display's
  resolution, refresh rate (current and highest), scaling and HDR state; every DXGI adapter with its LUID,
  memory and Direct3D 12 feature level, and whether a flip-discard swapchain on a D3D12 queue (what
  `dxgi-bridge` presents through) and a 10-bit HDR10 one can be created; every Vulkan device with its API and
  driver version, LUID, memory, queues, present modes, surface formats and extensions; implicit Vulkan layers,
  Vulkan and Java environment variables, the other installs and their per-program GPU preferences. The user's
  profile path and name are replaced before writing. The native calls (DXGI, D3D12, Vulkan) run in a separate
  `powershell.exe` with a 60 second limit, so a crashing or hanging driver is reported instead of taking the
  installer down. `install.ps1` downloads it first and, when the version has `windows.system`, refuses before
  downloading anything else if a requirement is not met (unless `INSTALL_SKIP_CHECKS=1`); a requirement it
  could not check is a warning. Any failed install writes a report with the error and prints where it is and
  `issuesUrl`. It also runs on its own: `irm <base>/diagnose.ps1 | iex`.
- **File associations** are per user (`HKCU\Software\Classes`, no admin rights). Each extension
  gets a ProgID `<id>.<ext>` whose open command passes the file as the last argument: `"app.exe"
  "%1"`, and for a jar `javaw` (or the `.cmd` launcher when `shortcuts.gui` is false). The binary
  is always listed under **Open with**. It becomes the default only when no other program has
  claimed the extension, because Windows does not let a program silently take over an existing
  file type. Executable types (`.exe`, `.bat`, `.ps1`, ...) are refused at generation time.
  A file type shows the binary's `icon` (or a native exe's own) unless its association names an
  `icon` of its own: an `.ico`, or a square `.png` converted like the binary's. Associations that
  name the same file share it; it ships once, as `<binary>-<file stem>.ico` next to the binary.
  The install record notes which defaults it set, so updates drop associations the new version no
  longer lists, and uninstall removes only what it added.
- **Archives** (`kind: archive`, a `.zip`) are verified, unpacked into `dir` (default: the install
  folder) and every extracted file is recorded, so updates remove files a newer archive dropped
  and uninstall removes them all. Use it for something like a jlink runtime image; `exposes`
  names the commands inside it (`java: bin/java.exe`), and generating fails if a path is not in
  the zip. An archive cannot also set `addToPath`, `shortcuts`, `icon`, `runtime` or `jvmArgs`.
  Jars in other installs point their `runtime` at an archive install's id.
- **Signing** (native exes): sign the file *first*, then generate, because the manifest hashes the file
  as given. `signedBy` (a subject such as `CN=Example Inc`) makes the installer refuse a download that
  is unsigned or signed by someone else, before anything is placed. By itself it also needs Windows to
  trust the signature. `signerThumbprint` pins one certificate instead, so a self-signed (snake-oil)
  certificate works for testing: it is accepted only if it is exactly that certificate, with a warning
  that this machine does not trust it. The SHA-256 already guarantees the file is the published one;
  the signature adds who published it.
- **Files** (`kind: file`, such as a licence or third-party notices) are downloaded, verified and placed like a
  binary, and removed by updates that drop them and by the uninstaller, but nothing runs them: they are not
  commands, and cannot set `addToPath`, `shortcuts`, `icon`, `fileAssociations`, `signedBy` or the jar options.
  A third-party notices file belongs next to a native exe whose image has libraries compiled in:
  `{ "name": "notices", "source": "THIRD-PARTY-NOTICES.txt" }`.
- **Install manifest**: written to `<installDir>\install-manifest.json` and to
  `<registryDir>\<id>.json`: every file with path/kind/version/hash, shortcuts, PATH entries
  and registry keys. `commands.<name>.path` is how separately installed apps find and start
  each other: on the VexelRay stack, `vexelray-framework`'s `Apps.find(id)` / `Apps.spawn(id, args...)`
  read it (honouring `INSTALL_REGISTRY_DIR`), which is how Vexplore opens a file in the Text Editor
  and the editor opens a file in Vexplore.
- **uninstall.ps1** (`uninstall.cmd`) scans `registryDir` for install manifests, so it finds
  every install (`-List`, `-Id`, `-All`, `-Yes`). It removes only what the manifest lists and
  leaves files the user added.
- **update.ps1** (`update.cmd`) compares per-binary versions in the latest manifest entry with
  the install record (`-Check`, `-Yes`), then runs the hash-verified `install.ps1`.

### On Linux

The Linux scripts are POSIX `sh` (dash, bash, busybox), and need `curl` or `wget`, `tar`, `awk` and `sha256sum`.
sh cannot read JSON, so they read `manifest.linux.txt` instead: the Linux part of every version in `manifest.json`,
one tab-separated record a line, rewritten from it on every run (its format is documented in `LinuxTarget`).

- **install.sh** works as `install.ps1` does, for the user only and without root: every download is checked
  against its SHA-256 before anything is placed, through the same cache (`<registryDir>/../cache`, resumed with
  `curl -C -`), and placing goes through `<registryDir>/<id>.journal`, so a failure, Ctrl+C or a killed run is
  rolled back (by the next run, for a killed one) and a run that got as far as its commit is finished. Files go to
  `installDir` (default `~/.local/opt/<id>`), executable; a `.tar.gz` is unpacked with its modes kept, after
  refusing an entry that would leave its folder; a jar gets a launcher script named after it, which finds Java
  through its `runtime`'s `<id>.home`, `JAVA_HOME` or `PATH`. `addToPath` links the command into `~/.local/bin`,
  never over a file that is not its own, and says so when `~/.local/bin` is not on `PATH` yet. Shortcuts are
  desktop entries (`~/.local/share/applications/<appId>.desktop`, or `vexelray-<id>-<name>.desktop` for a binary
  without an `appId`, and a launcher in the Desktop folder), with the binary's PNG icon. File types are a shared-mime-info package
  (`~/.local/share/mime/packages/vexelray-<id>.xml`) whose globs weigh less than the usual, so an extension
  another type has keeps it; a type without a `contentType` is the install's own (`application/x-<id>-<ext>`) and
  gets the association's icon in `hicolor`. The binary's desktop entry lists the types, and becomes the default
  (`xdg-mime default`) only for a type no program is the default of. The system requirements are checked as on
  Windows (the GPU through `vulkaninfo`, from `vulkan-tools`; without it the GPU is a warning, not a failure). The
  record is the same JSON as on Windows (`<registryDir>/<id>.json` and `install-manifest.json`, with
  `platform: linux`), beside `<id>.state`, the same in lines for the scripts. Options: `INSTALL_VERSION`,
  `INSTALL_DIR`, `INSTALL_NO_SHORTCUTS`, `INSTALL_NO_PATH`, `INSTALL_NO_ASSOCIATIONS`, `INSTALL_FORCE`,
  `INSTALL_SKIP_CHECKS`, `INSTALL_REGISTRY_DIR`, or `sh -s -- --version 1.2.3 --no-path ...`.
- **uninstall.sh** removes what the record lists (a link only while it is still a link), takes its entry out of
  `mimeapps.list`, and leaves files the user added (`--list`, `--id`, `--all`, `--yes`; it asks on the terminal
  otherwise, and refuses without one).
- **update.sh** compares the installed version with the manifest's latest Linux version (`--check`, `--yes`), then
  runs the hash-verified `install.sh` into the same folder with the same choices.

There is no window, no app manager and no diagnostic report on Linux yet.

### Renames: an upgrade removes what the old version named differently

**Rule:** when a new version puts something in place under a different name than the version before it did, the
upgrade must remove the old one, and carry over whatever the user attached to it. Anything left behind turns up as a
duplicate menu entry, a launcher that runs nothing, a default application that no longer exists, or a dock pin that
went blank. Check this every time a name derived from the config changes: a binary's `name`, `file` or `dir`, an
`appId`, the install `id`, or the naming scheme in the templates themselves.

What the Linux `install.sh` does about it today:

- **Files, shortcuts, links.** Every one is recorded by its full path in `<id>.state`. Whatever the last install
  recorded and this one does not is removed (step 6, through the backup, so a rollback restores it). A renamed
  desktop entry or launcher therefore goes away by itself.
- **Default applications.** A type whose default is an entry the last install registered, under whatever name, stays
  this install's default under the new name, and the old name is taken out of `mimeapps.list`.
- **Dock pins.** A GNOME favourite (`org.gnome.shell favorite-apps`) on the old entry is moved to the new one. The
  state records each binary's entry as `entry NAME DESKTOP-ID`, so the next rename knows the old name; for an install
  from before that record existed, the old name is the `vexelray-<id>-<name>.desktop` the installer used then.
- **Links on PATH.** A link the last install recorded is its own to replace, as is one the replaced install
  recorded (see `replaces` below).
- **Comparing with the old record.** The steps after the commit compare against a copy of the old `<id>.state` taken
  before the commit, because the commit replaces it. (Before this, they compared the new record with itself, and a
  default the old version had was never dropped.)

#### Renaming the install itself: `replaces`

A new `id` is a different install as far as the records go, so the config says what it used to be:

```json
"id": "viewer",
"replaces": [ { "id": "pix", "repoPath": "apps/pix" } ]
```

- **The installer** (both platforms), finding no install under its own id but one under a replaced id, carries that
  install's choices over (shortcuts, PATH, file types), installs into its own default folder (the old updater passes
  the old folder, which is ignored), and once it has committed, removes the old install with its own uninstaller
  (`uninstall.sh --id pix --yes`, `uninstall.ps1 -Id pix -Yes`). Anything both placed under the same name, such as a
  command on PATH, a Start menu shortcut or a desktop entry, is taken out of the old record first, so the uninstaller
  leaves it alone. Defaults and dock pins follow as above. If removing the old one fails, the new one stays installed
  and the installer says how to remove the old one.
- **The generator** writes the new application's `manifest.json`, `manifest.linux.txt` and install scripts to the
  replaced `repoPath` as well, with a README saying where it went. Old installs' updaters (and the apps' own update
  checks) still read the old manifest URL; they now find the new application's latest version there and run its
  installer, which does the above. That folder is beside the application's own when the output folder is its
  `repoPath` in a checkout of the repo (as `vexelray-dist/deploy.ps1` generates `apps/<id>`), and under `forward/` in
  the output folder otherwise. Keep `replaces` for as long as old installs may be out there: every release refreshes
  the forwarding copies.
- **The application** lists the old name in `@VexelApp(formerNames = ...)`, which moves its settings directory
  (`~/.<name>`), and the build checks the two lists agree (`vexelray-build/README.md`).

The Linux side is covered end to end by `tests/linux-smoke.sh`. The Windows side follows the same steps in
`install.ps1` but has not been run yet: try it on a Windows machine before relying on it.

Not covered yet: pins in other docks (KDE Plasma's task manager keeps `applications:<entry>` in its own config), and
Windows. Windows has no `appId` yet. When it gets one (an AppUserModelID on the shortcuts and the process), the Start
menu shortcuts and taskbar pins named after the old scheme need the same treatment in `install.ps1`, and `update.ps1`
and the app manager in `manager.ps1` need to agree with it.

The generated scripts are pure ASCII with LF endings, because their hashes are recorded in
`manifest.json` and must survive `irm | iex`, `curl | sh` and git.

## Adding a platform

Implement `PlatformTarget` (scripts, manifest section, README section; and, if its scripts need them, template
variables of their own, an icon format, checks, and companion files made from the manifest), put its templates
under `installer-core/src/main/resources/templates/<key>/`, add a section for it to `InstallerConfig`,
and register it in `InstallerGenerator`'s default target list.

## Known limits

- `uninstall` and `update` are PowerShell scripts with `.cmd` launchers, not compiled `.exe`s.
- Windows PowerShell 5.1 or newer; per-user install only (no admin, no HKLM).
- Linux: per-user only (no root, no `/opt`); x86_64 unless `arch` says otherwise. A dock pin follows a renamed
  desktop entry only in GNOME (see Renames). An application's file types
  and its menu entry show once the desktop rereads them, which the installer asks for when
  `update-desktop-database` and `update-mime-database` are installed.
- GitHub's raw host caches for a few minutes after a push.
