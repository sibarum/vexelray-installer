# vexelray-installer

Turns a native-image executable and/or a compiled uberjar into a one-line installer served
from a public GitHub repo.

```
your build ──► installer:generate ──► install.ps1  uninstall.ps1  update.ps1  diagnose.ps1  manifest.json  README.md
                                  └─► staged artifacts ──► installer:publish ──► GitHub release
```

Windows is supported today. The generator is platform-neutral and `manifest.json` is organised
per platform; macOS and Linux arrive as new `PlatformTarget`s with their own templates.

## Modules

| Module | What |
| --- | --- |
| `installer-core` | Build-tool-independent library: config and manifest model, `PlatformTarget`s, templates, GitHub release publisher. Also a runnable CLI jar (`-cli` classifier) for non-Maven projects. |
| `installer-maven-plugin` | Goals `installer:generate` and `installer:publish`. |

Build and test everything: `mvn install` (Java 21+). End to end on Windows:
`powershell -File tests\smoke.ps1`. The installer window: `powershell -File tests\window.ps1` (drives it
with the mouse, so it needs an unlocked desktop).

## Use from Maven

```xml
<plugin>
  <groupId>dev.vexelray.installer</groupId>
  <artifactId>installer-maven-plugin</artifactId>
  <version>0.1.0-SNAPSHOT</version>
  <executions><execution><goals><goal>generate</goal></goals></execution></executions>
  <configuration>
    <publisher>Example Inc</publisher>
    <windows>
      <binaries>
        <binary>
          <attached>main</attached>          <!-- the project's own (shaded) jar -->
          <file>myapp.jar</file>
          <javaMin>21</javaMin>
          <shortcuts><label>MyApp</label><startMenu>true</startMenu></shortcuts>
        </binary>
        <binary>
          <name>myapp-native</name>
          <source>target/myapp.exe</source>   <!-- e.g. from native-maven-plugin -->
          <addToPath>true</addToPath>
        </binary>
      </binaries>
    </windows>
  </configuration>
</plugin>
```

A complete example is in [tests/maven-sample](tests/maven-sample/pom.xml).

1. `mvn package` runs `generate`: the files to commit land in `target/installer/`, the
   artifacts to upload in `target/installer-assets/<version>/`.
2. `mvn package installer:publish` also creates the GitHub release `v<version>` and uploads the
   artifacts (token in `$GITHUB_TOKEN`, or the variable named by `-Dinstaller.tokenEnv`). Add
   `-Dinstaller.dryRun` to see what would be uploaded. `publish` is never bound to a phase.
3. Commit `install.ps1`, `uninstall.ps1`, `update.ps1`, `diagnose.ps1`, `manifest.json` and `README.md` from
   `target/installer/` to the project repo (or point `outputDirectory` at a checkout of it).
   The README contains the one-liner:
   ```powershell
   irm https://raw.githubusercontent.com/owner/project/main/install.ps1 | iex
   ```

Every run merges into the existing `manifest.json`, so every version ever published stays in its
`versions` history; `latest` is the highest non-prerelease. If `README.md` in the output dir was
not generated by this tool, the generated one is written as `INSTALL.md` instead.

### Plugin parameters

Defaults come from the project: `id` = artifactId, `name` = project name, `description`,
`version`, and `repo` from a github.com `<scm>` url.

| Parameter | Meaning |
| --- | --- |
| `id`, `name`, `publisher`, `description`, `version` | metadata; `id` is lowercase letters, digits, `. _ -` |
| `repo`, `branch`, `repoPath` | where the generated files are committed (`repoPath` for a subfolder); branch defaults to `main` |
| `releasesRepo`, `tagFormat` | where binaries are downloaded from; defaults `repo` and `v{version}` |
| `issuesUrl` | where people report problems; the diagnostic report says to attach itself there. Default: `https://github.com/<repo>/issues/new` |
| `windows.installDir` | default `%LOCALAPPDATA%\Programs\{name}` |
| `windows.registryDir` | where install manifests live; default `%LOCALAPPDATA%\vexelray-installer\installs` |
| `windows.binaries[]` | `source` *or* `attached` (`main` or a classifier), `name`, `file`, `kind` (`native`/`jar`/`archive`/`file`, inferred from the extension; a `.zip` is an archive, and a `.txt`, `.md`, `.html`, `.pdf` or `.rtf` a file), `dir`, `version`, `addToPath`, `icon` (an `.ico`, or a square `.png` of 256px or more that is converted to one; used by the shortcuts and the Apps entry), `shortcuts {desktop, startMenu, label, gui}`, `javaMin` (jars), `jvmArgs[]` (jars; placed before `-jar`), `runtime` (jars; id of an install that provides `binjava.exe`, found through the registry at launch), `exposes` (archives; `{command: path-inside-zip}`, recorded under `commands`), `signedBy` + `signerThumbprint` (native exes; see Signing), `fileAssociations[] {extension, description, contentType, icon}` (not archives; see File associations) |
| `windows.requires[]` | `{id, min}`: installs that must be present first. A binary's `runtime` is required implicitly. The installer refuses, before changing anything, if one is missing or older than `min`; the uninstaller warns when removing something another install still needs |
| `windows.system` | what the computer must have: `windows` (oldest version, `10.0.19041` or a build number), `memoryMb`, `diskMb` (free on the install drive), `vulkan` (`1.3`), `vulkanExtensions[]`, `d3d12` (feature level, `11_0` to `12_2`). The GPU fields must all be met by one GPU: its Vulkan device, and the DXGI adapter with the same LUID. See Diagnostics |
| `outputDirectory`, `assetsDirectory` | default `target/installer` and `target/installer-assets` |
| `notes`, `baseUrl`, `assetBaseUrl`, `skip` | release notes; URL overrides for testing; skip the goal |

## Use without Maven

```
mvn -pl installer-core package
java -jar installer-core/target/installer-core-0.1.0-SNAPSHOT-cli.jar --config installer.json \
     --version 1.2.0 --out dist [--publish]
```

`installer.json` has the same fields as the plugin configuration; see
[installer.example.json](installer.example.json). Relative `source` paths resolve against the
config file.

## Suites: one command for several applications

Applications that ship together can share one install command and one page of instructions, while each stays
an install of its own (its own folder, record, Apps entry, updater and uninstaller), published from its own
repo exactly as above. A suite names its members by their `installer.json`:

```json
{
  "id": "vexelray", "name": "VexelRay", "description": "...",
  "repo": "owner/site-repo", "repoPath": "docs/install",
  "members": [
    { "config": "../vexplore/installer.json", "page": "../apps/vexplore.html" },
    { "config": "../text-editor/installer.json" }
  ]
}
```

```
java -jar installer-core/target/installer-core-0.1.0-SNAPSHOT-cli.jar --suite suite.json --out docs/install
```

writes `install.ps1` and `README.md` (the install page), and needs neither the artifacts nor the network.
Commit both to `repo`/`repoPath`. The suite's `install.ps1` installs nothing itself: for each member, in the
listed order, it fetches the member's published `manifest.json`, downloads the member's own `install.ps1`,
refuses it unless it matches the SHA-256 the manifest records (`tools.install.ps1`), and runs it. A member
whose manifest is not published yet is skipped and reported. `INSTALL_ONLY=a,b` limits the run to some
members. `INSTALL_NO_SHORTCUTS`, `INSTALL_NO_PATH`, `INSTALL_NO_ASSOCIATIONS`, `INSTALL_FORCE` and `INSTALL_SKIP_CHECKS` pass through to
every member; `INSTALL_VERSION` and `INSTALL_DIR` name one application, so they are set aside. `page`
(optional) links a member's name on the install page; `manifestUrl` (optional) overrides the URL derived from
the member's `repo`, `branch` and `repoPath`.

### A landing page

A suite can also have a page of its own, served by GitHub Pages from a repo of its own (`owner.github.io`, say),
so the command is short and the first thing people find:

```json
{
  "site": {
    "url": "https://owner.github.io",
    "badge": "0.1.0 · prerelease",
    "tagline": "One line under the name.",
    "requirements": "Needs Windows 10 or 11.",
    "feedbackUrl": "https://github.com/owner/repo/issues/new",
    "accentColor": "#2563eb",
    "logo": "site/mark.svg",
    "heroAction": { "label": "What it is built on", "url": "https://owner.github.io/tech.html" },
    "links": [ { "label": "Docs", "url": "https://owner.github.io/docs/" } ],
    "footerLinks": [ { "label": "Licenses", "url": "https://owner.github.io/licenses.html" } ],
    "notice": "Small print at the foot of the page, such as trademark notices.",
    "sections": [
      {
        "id": "build", "title": "Build your own", "nav": "Developers",
        "lede": "A paragraph under the title.",
        "cards": [ { "stat": "1 line", "title": "Start", "text": "What it is.", "url": "https://owner.github.io/docs/start.html" } ],
        "action": { "label": "Read the guide", "url": "https://owner.github.io/docs/" }
      }
    ]
  },
  "members": [
    { "config": "../vexplore/installer.json", "page": "...", "image": "shots/vexplore.png", "imageAlt": "What it shows" }
  ]
}
```

```
java -jar installer-core/target/installer-core-0.1.1-SNAPSHOT-cli.jar --suite suite.json --site --out ../owner.github.io
```

writes `index.html`, a copy of the suite's `install.ps1` (so the command is `irm https://owner.github.io/install.ps1 | iex`),
each member's icon and screenshot under `img/` (and `site.logo` as `img/logo.svg` or `.png`), and `.nojekyll`. Only
`site.url` is required. The page is dark, with the name over a live backdrop that draws only while it is on screen. It shows the
command with a copy button (and `site.heroAction` as a button under it), a card for each member (its screenshot, or its icon when it has no `image`; its
`description`), and what the install changes on the computer, worked out from the members' configs: install
folders, shortcuts, the commands added to `PATH` and the applications that register file types. Each of
`site.sections` goes between the members and those details, as a title, a paragraph, a row of cards (a card's `url`
is optional, and so is its `stat`, a figure set large above its title) and an optional button, and gets a header link (`nav`, or its `title`) to its `id`. Text in the config
may use `` `code` ``; everything else is escaped. `site.footerLinks` go in the footer after the source link, and
`site.notice` is set in small print under them. The members' manifests stay where their own runs published them,
so installs and updaters are the same whichever command installed them. Publish the folder from its repo's root with
GitHub Pages (**Settings > Pages > Deploy from a branch**).

## What the generated files do

- **install.ps1** reads `manifest.json`, downloads each binary, verifies its SHA-256, then
  places files, unblocks them, writes a `<name>.cmd` launcher for each jar, creates shortcuts,
  registers file types, optionally edits the user PATH, and registers an Apps & features entry.
  Nothing is written to the install dir until every download has verified. Options:
  `INSTALL_VERSION`, `INSTALL_DIR`, `INSTALL_NO_SHORTCUTS`, `INSTALL_NO_PATH`,
  `INSTALL_NO_ASSOCIATIONS`, `INSTALL_FORCE`, `INSTALL_SKIP_CHECKS`, `INSTALL_QUIET`. The `NO_*` choices in effect are stored in the
  install record (`options`), and updates and reinstalls keep them; `INSTALL_NO_*=0` opts back in.
  Run from a console a person is at, it opens a WinForms window: the folder and the shortcut, PATH and
  file-type choices (filled from the options above and the last install), then a progress bar and the same
  log the console gets, then **Start** (the first shortcut), or for a failure the error, **Open report** and a
  link to `issuesUrl`. Unmet system requirements are asked about rather than refused, and Cancel stops any
  time before files are placed. `INSTALL_QUIET=1` (`-Quiet`), `CI`, `-NonInteractive` or redirected output
  keep it in the console; `update.ps1` and suite installs always run their installers quietly.
- **diagnose.ps1** (`diagnose.cmd`) checks the computer against `windows.system` and writes a text report
  for bug reports to `<registryDir>\..\diagnostics\<id>-<time>.txt` (the last ten are kept; `-Out`, `-Copy`,
  `-Json`): Windows edition and build, processor, memory, disk, GPU scheduling, power; each display's
  resolution, refresh rate (current and highest), scaling and HDR state; every DXGI adapter with its LUID,
  memory and Direct3D 12 feature level, and whether a flip-discard swapchain on a D3D12 queue (what
  `dxgi-bridge` presents through) and a 10-bit HDR10 one can be created; every Vulkan device with its API and
  driver version, LUID, memory, queues, present modes, surface formats and extensions; implicit Vulkan layers,
  Vulkan and Java environment variables, the other installs and their per-program GPU preferences. The user's
  profile path and name are replaced before writing. The native calls (DXGI, D3D12, Vulkan) run in a separate
  `powershell.exe` with a 60 second limit, so a crashing or hanging driver is reported instead of taking the
  installer down. `install.ps1` downloads it first and, when the version has `windows.system`, refuses before
  downloading anything else if a requirement is not met (unless `INSTALL_SKIP_CHECKS=1`); a requirement it
  could not check is a warning. Any failed install writes a report with the error and prints where it is and
  `issuesUrl`. It also runs on its own: `irm <base>/diagnose.ps1 | iex`.
- **File associations** are per user (`HKCU\Software\Classes`, no admin rights). Each extension
  gets a ProgID `<id>.<ext>` whose open command passes the file as the last argument: `"app.exe"
  "%1"`, and for a jar `javaw` (or the `.cmd` launcher when `shortcuts.gui` is false). The binary
  is always listed under **Open with**. It becomes the default only when no other program has
  claimed the extension, because Windows does not let a program silently take over an existing
  file type. Executable types (`.exe`, `.bat`, `.ps1`, ...) are refused at generation time.
  A file type shows the binary's `icon` (or a native exe's own) unless its association names an
  `icon` of its own: an `.ico`, or a square `.png` converted like the binary's. Associations that
  name the same file share it; it ships once, as `<binary>-<file stem>.ico` next to the binary.
  The install record notes which defaults it set, so updates drop associations the new version no
  longer lists, and uninstall removes only what it added.
- **Archives** (`kind: archive`, a `.zip`) are verified, unpacked into `dir` (default: the install
  folder) and every extracted file is recorded, so updates remove files a newer archive dropped
  and uninstall removes them all. Use it for something like a jlink runtime image; `exposes`
  names the commands inside it (`java: bin/java.exe`), and generating fails if a path is not in
  the zip. An archive cannot also set `addToPath`, `shortcuts`, `icon`, `runtime` or `jvmArgs`.
  Jars in other installs point their `runtime` at an archive install's id.
- **Signing** (native exes): sign the file *first*, then generate, because the manifest hashes the file
  as given. `signedBy` (a subject such as `CN=Example Inc`) makes the installer refuse a download that
  is unsigned or signed by someone else, before anything is placed. By itself it also needs Windows to
  trust the signature. `signerThumbprint` pins one certificate instead, so a self-signed (snake-oil)
  certificate works for testing: it is accepted only if it is exactly that certificate, with a warning
  that this machine does not trust it. The SHA-256 already guarantees the file is the published one;
  the signature adds who published it.
- **Files** (`kind: file`, such as a licence or third-party notices) are downloaded, verified and placed like a
  binary, and removed by updates that drop them and by the uninstaller, but nothing runs them: they are not
  commands, and cannot set `addToPath`, `shortcuts`, `icon`, `fileAssociations`, `signedBy` or the jar options.
  A third-party notices file belongs next to a native exe whose image has libraries compiled in:
  `{ "name": "notices", "source": "THIRD-PARTY-NOTICES.txt" }`.
- **Install manifest**: written to `<installDir>\install-manifest.json` and to
  `<registryDir>\<id>.json`: every file with path/kind/version/hash, shortcuts, PATH entries
  and registry keys. `commands.<name>.path` is how separately installed apps find and start
  each other: on the VexelRay stack, `vexelray-framework`'s `Apps.find(id)` / `Apps.spawn(id, args...)`
  read it (honouring `INSTALL_REGISTRY_DIR`), which is how Vexplore opens a file in the Text Editor
  and the editor opens a file in Vexplore.
- **uninstall.ps1** (`uninstall.cmd`) scans `registryDir` for install manifests, so it finds
  every install (`-List`, `-Id`, `-All`, `-Yes`). It removes only what the manifest lists and
  leaves files the user added.
- **update.ps1** (`update.cmd`) compares per-binary versions in the latest manifest entry with
  the install record (`-Check`, `-Yes`), then runs the hash-verified `install.ps1`.

The generated scripts are pure ASCII with LF endings, because their hashes are recorded in
`manifest.json` and must survive `irm | iex` and git.

## Adding a platform

Implement `PlatformTarget` (scripts, manifest section, README section), put its templates under
`installer-core/src/main/resources/templates/<key>/`, add a section for it to `InstallerConfig`,
and register it in `InstallerGenerator`'s default target list.

## Known limits

- `uninstall` and `update` are PowerShell scripts with `.cmd` launchers, not compiled `.exe`s.
- Windows PowerShell 5.1 or newer; per-user install only (no admin, no HKLM).
- GitHub's raw host caches for a few minutes after a push.
