# vexelray-installer

Turns a native-image executable and/or a compiled uberjar into a one-line installer served
from a public GitHub repo.

```
installer.json + artifacts  --build.ps1-->  install.ps1  uninstall.ps1  update.ps1  manifest.json  README.md
```

Windows is supported today. `manifest.json` is organised per platform so macOS and Linux can
be added without changing its shape.

## Use

1. `copy installer.example.json installer.json` and edit it (fields below).
2. Build your artifacts, then generate:
   ```powershell
   ./build.ps1 -Version 1.2.0 -Notes "What changed"
   ```
   Output goes to `dist/` (change with `-OutDir`, e.g. a checkout of the project repo).
   Artifacts are staged in `build/release-assets/<version>/`.
3. Upload those artifacts to the GitHub release tagged `v1.2.0` (or add `-Publish` to have
   the `gh` CLI create the release and upload them).
4. Commit `install.ps1`, `uninstall.ps1`, `update.ps1`, `manifest.json` and `README.md` from
   the output dir to the project repo. The README contains the one-liner:
   ```powershell
   irm https://raw.githubusercontent.com/owner/project/main/install.ps1 | iex
   ```

Re-run `build.ps1` with a new `-Version` for every release. `manifest.json` is merged, so
every version ever published stays in its `versions` history; `latest` is the highest
non-prerelease. If `README.md` in the output dir was not generated by this tool, the
generated one is written as `INSTALL.md` instead of overwriting it.

## installer.json

| Field | Meaning |
| --- | --- |
| `id` | lowercase id; names the install record and the Apps entry |
| `name`, `publisher`, `description` | display metadata |
| `version` | default version (overridden by `-Version`) |
| `repo`, `branch`, `repoPath` | where the generated files are committed (`repoPath` for a subfolder) |
| `releasesRepo`, `tagFormat` | where binaries are downloaded from; default `repo` and `v{version}` |
| `registryDir` | where install manifests live; default `%LOCALAPPDATA%\vexelray-installer\installs` |
| `windows.installDir` | default `%LOCALAPPDATA%\Programs\{name}` |
| `windows.binaries[]` | `source` (required), `name`, `file`, `kind` (`native`/`jar`, auto from extension), `dir`, `version`, `addToPath`, `shortcuts {desktop, startMenu, label, gui}`, `javaMin` (jars) |

Paths in `source` are relative to the config file.

## What the generated files do

- **install.ps1** reads `manifest.json`, downloads each binary, verifies its SHA-256, then
  places files, unblocks them, writes a `<name>.cmd` launcher for each jar, creates shortcuts,
  optionally edits the user PATH, and registers an Apps & features entry. Nothing is written
  to the install dir until every download has verified. Options: `INSTALL_VERSION`,
  `INSTALL_DIR`, `INSTALL_NO_SHORTCUTS`, `INSTALL_NO_PATH`, `INSTALL_FORCE`.
- **Install manifest**: written to `<installDir>\install-manifest.json` and to
  `<registryDir>\<id>.json`: every file with path/kind/version/hash, shortcuts, PATH entries
  and registry keys.
- **uninstall.ps1** (`uninstall.cmd`) scans `registryDir` for install manifests, so it finds
  every install (`-List`, `-Id`, `-All`, `-Yes`). It removes only what the manifest lists and
  leaves files the user added.
- **update.ps1** (`update.cmd`) compares per-binary versions in the latest manifest entry with
  the install record (`-Check`, `-Yes`), then runs the hash-verified `install.ps1`.

The generated scripts are pure ASCII and written with LF endings, because their hashes are
recorded in `manifest.json` and must survive `irm | iex` and git.

## Known limits

- `uninstall` and `update` are PowerShell scripts with `.cmd` launchers, not compiled `.exe`s.
- Windows PowerShell 5.1 or newer; per-user install only (no admin, no HKLM).
- GitHub's raw host caches for a few minutes after a push.
